### 1. B-Tree
- 인덱스의 자료구조 ( 루트노드-브랜치노드-리프노드로 이루어짐 + 리프노트는 데이터포인터를 가짐 )
- 컬럼값을 트리구조로 정렬하여 저장
    - 탐색시간 : 기본적으로 FullScan은 O(N) 소요, B트리는 O(logN)소요
    - 모든 요소에 접근할 수 있는 균형잡힌 트리구조
- 대수확장성 : 트리깊이가 노드수에 비해 느리게 성장, 기본적으로 인덱스 한깊이 증가시 저장가능한 항목수 4배증가

### 2. B-Tree와 B+Tree
어디에 실제 데이터(포인터)를 두는가의 차이
- B-Tree는 내부노드, 리프노드에 모두 데이터(포인터)를 가짐
    - 키 + 데이터의 중복저장이 없음
- B+Tree는 리프노드에 데이터(포인터)를 가짐
    - fan-out의 극대화
    - 범위검색이 압도적으로 빠름 ( 시작 리프노드 찾고 → 옆쪽 스캔, 트리재탐색 없음 )
    - ORDER BY / MIN / MAX 최적화 ( 리프노드가 정렬상태로 연결되어 추가정렬 필요없음 )

| **구분** | **B-Tree** | **B+Tree** |
| --- | --- | --- |
| 데이터 위치 | 내부 + 리프 | **리프만** |
| 내부 노드 | 키 + 데이터 | **키만** |
| 리프 연결 | ❌ | **⭕ (연결 리스트)** |
| 범위 검색 | 느림 | **빠름** |
| fan-out | 작음 | **큼** |
| DB 인덱스 | 거의 ❌ | **표준 ⭕** |

 ### 3. 인덱스 최적화 기법
 (1) 인덱스는 비용이다.
- 읽기비용 : 인덱스는 두번 탐색을 강요 ( 인덱스 트리 리스트 탐색 → 컬렉션(테이블) 탐색 )
- 쓰기비용 : 컬렉션(테이블)이 삽입/수정되면 인덱스도 함께 수정필요
- 트리 높이를 균형있게 조절하는 비용 발생

(2) 테스팅을 통해 적절한 패턴찾기
서비스의 테이블 크기, 데이터 분포, 쿼리패턴, 캐시상태 등에 따라 전부 다르기 때문이다.
EXPLAIN : DB가 해당 쿼리를 어떻게 실행할지 미리 보여주는 명령
→ 인덱스 사용여부, 어떤 인덱스 사용, 테이블 접근 방식, 예상 읽기 행수 등을 보여줌

(3) 복합 인덱스는 같음, 정렬, 다중값, 카디널리티 순이다.
복합인덱스 생성에서는 왼쪽값부터 정렬 → 범위를 크게 줄여주는 것부터 인덱스를 구성
- 우선순위 : 같음조건 컬럼(==, equal) → 정렬대상 컬럼(order by) → 범위조건 컬럼(≥, ≤, between, in)
- 동일조건에서는 카디널리티(유니크한 정도)가 높은 순서를 앞에 배치한다.
