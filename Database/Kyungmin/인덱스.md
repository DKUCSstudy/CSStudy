### ✅ B-Tree
- DB 인덱스의 자료구조 ( 루트노드-브랜치노드-리프노드로 구성 )
- 리프 노드에 데이터(포인터) 저장
- 탐색 시간: O(log N) <-> Full Scan의 소요시간 O(N)
- 대수확장성 : 트리깊이가 노드수에 비해 느리게 성장, 기본적으로 인덱스 한깊이 증가시 저장가능한 항목수 4배증가

### ✅ B+Tree
- 실제 DB 인덱스 표준 자료구조
- 데이터는 반드시 리프노드에만 저장
- 내부 노드는 키만 저장 → fan-out 증가
- 리프 노드가 정렬 + 연결 리스트 구조
- 범위 검색, ORDER BY, MIN/MAX 매우 빠름

### ✅ B-Tree vs B+Tree
| **구분** | **B-Tree** | **B+Tree** |
| --- | --- | --- |
| 데이터 위치 | 내부 + 리프 | **리프만** |
| 내부 노드 | 키 + 데이터 | **키만** |
| 리프 연결 | ❌ | **⭕ (연결 리스트)** |
| 범위 검색 | 느림 | **빠름** |
| fan-out | 작음 | **큼** |
| DB 인덱스 | 거의 ❌ | **표준 ⭕** |

### ✅ MySQL InnoDB의 인덱스 구조
- 클러스터드 인덱스
  - 리프 노드 = 데이터 행
  - 테이블당 1개

- 클러스터드 인덱스 우선순위
  - 1순위) PRIMARY KEY
  - 2순위) UNIQUE NOT NULL
  - 3순위) 숨겨진 row_id
 
- 세컨더리 인덱스
  - 리프 노드에 PK 저장
  - PK로 클러스터드 인덱스 재탐색
  - 세컨더리 인덱스 생성방식
  `CREATE INDEX idx_name ON table(column);`

### ✅ 인덱스 최적화의 핵심
(1) 인덱스는 비용을 고려
- 읽기비용 : 2번 탐색 (인덱스 → 데이터)
- 쓰기비용: INSERT/UPDATE 시 인덱스도 수정

(2) 복합인덱스의 컬럼지정 순서
- 같음조건(=)
- 정렬 (ORDER BY)
- 범위 조건 (<, >, BETWEEN)
같은 조건이면 카디널리티 높은 컬럼 우선
